# 微信小程序开发发布 SOP（双机协作场景）

> 适用：微信小程序（含蓝牙硬件类）的修改、上传、审核、发布、Git 合并全流程。
> 场景：家里 Mac 开发 + 公司 Mac / 同事公司电脑真机测试 + 单个管理员微信账号。
> 来源：祈福牌蓝牙小程序 v1.0.2 发布实践（2026-04-20）。

---

## 0. 前置条件

- 项目已用 Git 托管，远程在 GitHub/Gitee。
- 本机已登录微信开发者工具，扫码账号 = 小程序管理员微信。
- 本机 Node.js、Git、网络均正常。
- 代码里 `project.config.json` 的 `appid` 是正确的真实 AppID，不是 `testappid`。
- （双机场景）两台 Mac 均能访问同一远程仓库。

---

## 1. 开始前：校准代码与环境

在终端进入项目根：

```bash
cd <项目根目录>
git fetch origin
git status
git log --oneline HEAD..origin/main
```

- `git status` 显示 `up to date with 'origin/main'` → 代码最新。
- 第 3 条命令无输出 → 本地 main 未落后。
- 有未提交的历史改动（modified/deleted/untracked）也没关系，记住它们即可，新功能分支独立提交。

**坏 ref 小坑**：macOS 同步/双机场景偶尔产生 `refs/heads/main 2` 之类坏 ref，`git fetch` 会报 `bad object`；删除 `.git/refs/heads/main 2` 后重试即可。

---

## 2. 新建功能分支（双机规范必做）

```bash
git checkout -b feat/<短描述>
```

例：`feat/miniprogram-hide-tricolor-and-protocol`

**禁止在 `main` 直接改**，即使改动很小；这是双机协作的硬约束。

---

## 3. 改代码 · UI 变更原则

- **隐藏优于删除**：功能从 UI 移除时，优先"注释掉"而不是物理删除；协议层、底层常量保留（便于快速恢复、避免协议不一致）。
- **最小改动**：本次要做什么就做什么，不顺手重构、不顺手改颜色/按钮样式（触发"过度工程化"反模式）。
- **WXML 遍历数组的场景**：改数据源（`modes` / `colors` 等 `data` 里的数组）即可，WXML/WXSS 一般无需改。
- **删除整块 UI 区域**：WXML 删对应 `<view>`、WXSS 删对应类选择器，保持文件干净。

---

## 4. 本机验证（微信开发者工具模拟器）

1. 打开微信开发者工具，导入项目：
   - 项目名称：随便起（只是本机标签，与小程序身份无关）
   - 目录：选 `miniprogram` 目录（或对应小程序根）
   - **AppID**：工具会自动读 `project.config.json`，**无需手动填**
   - **后端服务**：务必选"**不使用云服务**"（除非项目真用云开发）
   - **开发模式**：**小程序**（左侧第 1 个入口；不要选"多端应用"）
2. 首次进入弹出的 Git 扩展提示 → **点 Never**（避免显示父级整个仓库的改动，干扰小程序编辑）。
3. `⌘ + S` 保存 → `⌘ + B` 编译 → 右侧模拟器刷新。
4. **蓝牙类小程序**在模拟器里没有真实 BLE，进不去控制页：在 Console 面板（底部）输入以下命令直跳：

   ```js
   wx.navigateTo({ url: '/pages/<目标页路径>' })
   ```

   命令行见项目实际路由（如 `/pages/control/control`）。
5. 按 UI 改动清单肉眼核对：文字、布局、按钮数量、交互反馈等。
6. **模拟器验证通过 ≠ 真机通过**，模拟器只保证 UI 正确，硬件通信必须真机（第 8 步体验版）。

---

## 5. 上传到微信后台"开发版"

1. 微信开发者工具右上角 → **上传**。
2. 弹窗"上传成功后，需要联系管理员..."：**这是通用提示文案**（所有人都会看到），不代表权限不足；管理员本人也会看到这条。直接点**确定**。
3. 填写上传表单：
   - **更新类型**：
     - `版本升级` → 主版本 +1，不兼容或重大改版
     - `特性更新` → 次版本 +1，新功能
     - **`修订补丁` → 修订号 +1，小修复/UI 微调（最常用）**
     - `上次填写` → 少用
   - **版本号**：按语义化版本规则（`major.minor.patch`）。工具会根据"更新类型"自动填。
   - **项目备注**：**务必清空默认时间戳，手动填写**（例：`v1.0.2 隐藏「三色变换」效果选项、移除底部冗余的「通信协议」开发信息区块`）。3 个月后回顾时，默认时间戳信息量为 0，手动备注才有用。
4. 点"上传" → 等待 5~30 秒 → 弹出"**代码上传成功**"绿色对勾即完成。
5. 登录 https://mp.weixin.qq.com → 左侧菜单 **管理 → 版本管理** → **`⌘ + ⇧ + R`** 强制刷新（普通刷新可能走缓存看不到）→ "开发版本"区块应出现刚上传的版本。

---

## 6. 设为"体验版"

在版本管理页"开发版本"区块：

1. 目标版本右侧：点"提交审核"按钮**旁边的下拉箭头 `v`**（不是绿色按钮本身！）。
2. 菜单里选"**设为体验版**" → 确认。
3. 页面出现二维码（或左侧菜单 **管理 → 成员管理 → 体验成员** 里看到二维码入口）。

---

## 7. 真机验证（给有硬件的同事 / 自己真机）

### 7.1 确认测试人员是"体验成员"

左侧 **管理 → 成员管理 → 体验成员** 标签：
- 列表里有对方的微信 → 直接发二维码
- 没有 → 点"+ 添加成员" → 输入对方微信号 → 对方在微信里接受邀请 → 再发二维码

### 7.2 测试清单（按项目实际情况裁剪）

```
UI 层
  □ 扫码能打开小程序，顶部有"体验版"标识
  □ 本次改动的 UI 符合预期
  □ 页面整体布局无错位、滚动正常

硬件层（需要真实设备）
  □ 硬件扫描/连接成功
  □ 核心功能命令真机生效
  □ 异常路径（如断开/失败）提示正常
```

### 7.3 反馈不通过怎么办

回到本机修复 → 上传版本号 +1（例：1.0.2 → 1.0.3） → 重新设为体验版；**不要在原版本号上覆盖上传**，微信后台以版本号为主键。

---

## 8. 提交审核

真机验证通过后，在版本管理页的"开发版本"区块：

1. 点目标版本右侧的**绿色"提交审核"按钮**（不是下拉）。
2. 表单常见字段：
   - **小程序服务类目**：若未变更保持默认。
   - **本次更新说明**（给用户看的，显示在微信"最近更新"里）：**用户语言**而非开发细节。例：`优化效果选择界面，提升操作体验`。**不要写**"隐藏三色变换"这种。
   - **功能页面**：保持默认（通常是首页路径）。
   - **是否需要登录**：按实际情况选。若"无需登录"、"无需测试号"直接注明。
   - **审核备注**：**开发者语言、写给审核员**。包含：改了什么、不影响哪些功能、审核员验证建议（如"无硬件时 UI 可看，完整链路需要硬件"）。
3. 勾选平台运营规范 → **提交审核**。
4. 版本移动到"**审核版本**"区块，状态"审核中"。

### 审核时长与结果通知

- 常规 1~24 小时，简单 UI 改动偶尔 10~30 分钟内完成。
- 结果推送到微信"**小程序管理**"公众号（需先关注）。
- 不通过 → 后台会显示拒绝原因 → 按要求改 → 版本号 +1 → 重走第 5~8 步。

---

## 9. 审核通过 → 点"发布"

**审核通过不会自动上线**，必须手动点"发布"。

1. 在"审核版本"区块，目标版本旁会出现"**发布**"按钮。
2. 点击 → 确认 → **瞬间生效**，所有用户下次打开即为新版本。

---

## 10. Git 合并 + 分支清理（发布后才做）

**合并时机原则**：`main` 应代表"已发布状态"，**功能分支在已发布到生产后才合并**，避免 main 含"尚未上线的代码"。

```bash
cd <项目根>
git checkout main
git pull origin main
git merge --no-ff feat/<你的分支> -m "Merge: <简短描述>"
git push origin main

# 删除已合并分支（本地 + 远程）
git branch -d feat/<你的分支>
git push origin --delete feat/<你的分支>
```

`--no-ff` 保留合并 commit，`git log` 里能清晰看到功能合并点；不建议对功能分支 fast-forward。

---

## 11. 写运维记录（按个人 Rules 约定）

在 `~/Documents/my-ops-log/<项目名>/YYYY-MM.md` 追加一条：

```markdown
## YYYY-MM-DD [小程序/发布] v1.x.y 审核通过并上线
- **操作**：一句话摘要
- **涉及**：应用(名称, AppID) / 代码仓库
- **变更**：
  - 微信后台：版本号变化
  - Git：合并 commit、分支清理情况
- **备注**：未同步合并的关联分支、待办项
```

写完后在 `my-ops-log` 仓库手动 `git add . && git commit && git push`。

---

## 12. 双机同步提醒

在另一台 Mac 开工前：

```bash
cd <项目根>        && git pull
cd ~/Documents/my-ops-log  && git pull
```

或对 Cursor 说"**同步环境配置**" + "**同步运维记录**"。

## 常见踩坑 Q&A

### Q1：上传/审核按钮灰或点了无反应？
A：检查你在微信后台的角色。管理员 / 运营者 / 开发者 有不同权限；参考 `mp.weixin.qq.com → 管理 → 成员管理` 里你自己的身份。

### Q2：上传后网页看不到新版本？
A：浏览器缓存。强制刷新 `⌘ + ⇧ + R`。若仍无，再检查开发者工具是否有"代码上传成功"绿色提示。

### Q3：体验版二维码扫出来"无权限"？
A：扫码人未加入"体验成员"。后台添加后让对方在微信里接受邀请。

### Q4：审核不通过，常见原因？
A：类目不符 / 更新说明违规词 / 功能与类目不一致 / 测试账号无法登录 / 首次发布资质问题。修复后版本号 +1 重提。

### Q5：线上已发布但用户说没变化？
A：小程序客户端有缓存。让用户在微信里"发现 → 小程序"长按该小程序 → "删除"，再重新打开；或等微信自动更新（一般几小时内）。

### Q6：tracked 了 `.DS_Store` 怎么办？
A：
```bash
echo ".DS_Store" >> .gitignore
git rm --cached .DS_Store
git add .gitignore && git commit -m "chore: ignore .DS_Store"
```

### Q7：`project.config.json` / `project.private.config.json` 自动变化要不要提交？
A：`.private.` 后缀的是本机私有配置，原则上应在 `.gitignore` 里。公共的 `project.config.json` 若仅是本机 editor 偏好变化（libVersion / editorSetting），不建议随功能分支一起提交，避免本机偏好污染他人环境。

## 命令速查

```bash
# 代码仓库
git fetch origin
git checkout -b feat/<描述>
git add <具体文件>
git commit -m "feat(miniprogram): ..."
git push -u origin feat/<描述>

# 发布后合并
git checkout main
git pull origin main
git merge --no-ff feat/<描述> -m "Merge: ..."
git push origin main
git branch -d feat/<描述>
git push origin --delete feat/<描述>

# 微信开发者工具
⌘ + S   # 保存
⌘ + B   # 编译
⌘ + P   # 按文件名跳转
⌘ + ⇧ + F # 全项目搜索
⌘ + F   # 当前文件搜索
```
